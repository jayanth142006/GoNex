# GoNex Backend — Requirements

## 1. Overview

GoNex is the AI help assistant for **CryptoNet**.

The GoNex backend must be developed and deployed as a **completely independent backend service**.

The CryptoNet frontend will consume GoNex through a public HTTPS API.

The backend developer is responsible only for the GoNex backend, AI integration, deployment, API, security, and related infrastructure.

The CryptoNet frontend is handled separately.

---

## 2. Core Requirement

Expose a simple HTTP API that allows the CryptoNet frontend to:

1. Send a user's message to GoNex.
2. Receive GoNex's response.
3. Optionally maintain a conversation using a conversation/session identifier.

The frontend should not need to know or care about:

* Which LLM is being used
* How prompts are constructed
* How context is retrieved
* Whether RAG/vector search is used
* How the knowledge base is stored
* How the AI is deployed

All of this must remain inside the GoNex backend.

---

# 3. API

## 3.1 Chat Endpoint

### `POST /api/chat`

This is the primary endpoint that the CryptoNet frontend will consume.

### Request

```json
{
  "message": "How does CryptoNet work?",
  "conversationId": "optional-conversation-id"
}
```

`message` is required.

`conversationId` is optional.

If conversation state is supported, the backend should use this identifier to maintain context.

---

### Response

```json
{
  "reply": "CryptoNet allows users to create payment requests and complete the payment through its UPI and crypto payment flow.",
  "conversationId": "conversation-id"
}
```

`reply` is required.

`conversationId` may be returned/generated by the backend if conversation management is implemented.

---

## 3.2 Health Endpoint

### `GET /health`

Used to verify that the GoNex service is running.

Example response:

```json
{
  "status": "ok"
}
```

---

# 4. Error Handling

The API must return appropriate HTTP status codes.

At minimum:

* `200` — successful request
* `400` — invalid request
* `401` / `403` — unauthorized request if authentication is implemented
* `429` — rate limit exceeded
* `500` — internal server error
* `503` — AI service temporarily unavailable

Error responses should have a consistent structure.

Example:

```json
{
  "error": "Unable to process the request."
}
```

Do not expose internal errors, API keys, stack traces, prompts, or infrastructure details to the frontend.

---

# 5. CORS

The backend must support CORS so that the CryptoNet frontend can communicate with it from the browser.

The allowed frontend origin must be configurable through environment variables.

Do not hard-code development-only origins.

Example:

```env
ALLOWED_ORIGINS=https://cryptonet-frontend.example
```

Development origins may also be configured when required.

---

# 6. HTTPS

The deployed GoNex API must be accessible through HTTPS.

The final deliverable must provide a public API base URL.

Example:

```text
https://gonex.example.com
```

The frontend should only communicate with the HTTPS endpoint.

---

# 7. AI Integration

The backend must handle the complete AI interaction.

The frontend must never directly communicate with the LLM provider.

The backend is responsible for:

* LLM API communication
* System prompt
* CryptoNet context
* Context retrieval/RAG if used
* Conversation handling if implemented
* Response generation
* Error handling
* Rate limiting where appropriate

The LLM provider/API key must remain server-side.

---

# 8. CryptoNet Knowledge

GoNex must be specifically knowledgeable about CryptoNet.

The provided `context.md` file contains the functional knowledge of CryptoNet.

The backend developer should use this information as the source of truth for the assistant.

The implementation may use:

* A direct context/system-prompt approach
* RAG
* Vector search
* Document retrieval
* Any other suitable approach

The implementation choice is left to the backend developer.

The important requirement is that GoNex provides accurate, CryptoNet-specific answers.

---

# 9. AI Behaviour

GoNex should behave as a **help assistant for CryptoNet**, not as a general-purpose chatbot.

It should:

* Explain CryptoNet clearly.
* Help users understand the payment process.
* Explain payment states.
* Guide users through the application.
* Explain terminology.
* Help troubleshoot common issues.
* Answer frequently asked questions.
* Explain blockchain/crypto concepts when relevant to CryptoNet.
* Prefer the provided CryptoNet context over general assumptions.
* Admit when information is unavailable.

GoNex must not invent CryptoNet functionality.

If the information is not available in the provided context, it should clearly say that it does not have enough information rather than hallucinating an answer.

---

# 10. Financial / Transaction Safety

GoNex is an informational assistant.

It must NOT:

* Execute payments.
* Sign blockchain transactions.
* Move funds.
* Access private keys.
* Request or store wallet private keys.
* Request seed phrases.
* Execute smart-contract transactions.
* Modify payment records.
* Claim that a transaction succeeded without verified information.
* Invent transaction hashes or payment statuses.

GoNex should never ask users for sensitive wallet credentials.

---

# 11. CryptoNet Integration

The initial version should remain independent from the CryptoNet backend.

No direct database access is required.

No direct access to CryptoNet's private infrastructure is required.

No blockchain write access is required.

If future read-only integrations are introduced, they should be added explicitly through controlled APIs.

The initial GoNex version should primarily operate using the provided CryptoNet knowledge/context.

---

# 12. Environment Configuration

Secrets and deployment-specific configuration must be handled through environment variables.

At minimum, configuration should support:

```env
LLM_API_KEY=
ALLOWED_ORIGINS=
```

Additional variables may be added depending on the implementation.

Secrets must not be committed to the repository.

---

# 13. Rate Limiting / Abuse Protection

The public API should have basic protection against abuse.

At minimum, consider:

* Request rate limiting
* Request size limits
* Input validation
* Appropriate timeouts
* Protection against excessively large prompts

The exact implementation is left to the backend developer.

---

# 14. Deployment

The GoNex backend must be independently deployable and hosted.

The backend developer is responsible for:

* Server/application setup
* Environment configuration
* AI provider configuration
* Deployment
* HTTPS
* CORS
* Production configuration
* Basic monitoring/logging
* API availability

The final output must include the production API base URL.

Example:

```text
https://gonex.example.com
```

---

# 15. Frontend Contract

The CryptoNet frontend developer should only need:

```text
GoNex Base URL
```

and the API contract.

The intended integration should be approximately:

```text
POST {GONEX_BASE_URL}/api/chat
```

with:

```json
{
  "message": "user message",
  "conversationId": "optional-id"
}
```

and receive:

```json
{
  "reply": "GoNex response",
  "conversationId": "id"
}
```

The frontend must not need to implement any AI logic.

---

# 16. Deliverables

The backend developer should provide:

1. Complete GoNex backend source code.
2. Deployed production API.
3. Production HTTPS URL.
4. API documentation.
5. Request/response examples.
6. Environment-variable documentation.
7. CORS configuration.
8. Error response documentation.
9. Deployment instructions.
10. Any required knowledge-base/RAG setup.
11. Basic API testing instructions.

The backend should be ready for direct integration into the CryptoNet frontend.

---

# 17. Separation of Responsibilities

### GoNex Backend Developer

Responsible for:

* AI
* Backend
* API
* Context/knowledge handling
* RAG if required
* LLM integration
* Security
* CORS
* Rate limiting
* Deployment
* HTTPS
* Documentation

### CryptoNet Frontend Developer

Responsible for:

* Chat button
* Chat window
* Chat UI
* Sending messages
* Displaying responses
* Loading/error states
* Connecting to the GoNex API

The frontend developer should not need to modify the GoNex backend.

---

# 18. Final Success Criteria

The project is considered complete when:

1. GoNex is independently hosted.
2. A public HTTPS API is available.
3. `POST /api/chat` works.
4. `GET /health` works.
5. CORS allows the CryptoNet frontend.
6. AI responses are based on CryptoNet context.
7. The backend does not expose secrets.
8. The backend does not require access to CryptoNet's database or private infrastructure.
9. The frontend can integrate using only the documented API.
10. The service can continue operating independently of the CryptoNet frontend.

**The exact AI technology, framework, LLM provider, RAG implementation, database/vector store, and hosting platform are implementation decisions left to the GoNex backend developer.**
